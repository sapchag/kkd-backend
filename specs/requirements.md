# requirements.md

Что делает решение и критерии приёмки.

## Назначение

Модуль ККД (контроль качества данных) проверяет качество данных по целям и ключевым результатам, которые сотрудники заносят в корпоративную систему управления целями. Если данные некорректны — целеполагание работает неэффективно, а руководство не видит реальной картины.

Модуль выполняет периодические **прогоны** ККД (планируется еженедельно): для каждого среза данных запускаются правила, находятся проблемы и сохраняются результаты с привязкой к прогону. Руководители и администраторы видят на странице ККД метрики качества, найденные проблемы и **дельту** с предыдущим прогоном.

## Функциональные требования

### Правила ККД

Реализованы 4 правила (из перечня задания). Применяются только к **активным** целям и их КР.

| Код | Важность | Условие нарушения |
|---|---|---|
| `GOAL_NO_OWNER` | critical | активная цель не имеет ответственного |
| `GOAL_NO_KR` | critical | у активной цели нет ни одного ключевого результата |
| `KR_WEIGHTS_SUM` | major | сумма весов КР активной цели ≠ 100% |
| `CASCADE_NO_PARENT` | major | активная цель в подразделении-потомке не связана с целью вышестоящего уровня |

Активная цель = `status = 'ACTIVE'`.

Логика правил вынесена в отдельный компонент (`RuleEngine`), который получает снимок данных и возвращает список проблем; не зависит от слоя API и доступа к данным.

### Схема БД

Хранит: подразделения с иерархией, цели (ответственный, родительская цель, статус, срок), ключевые результаты (целевое и фактическое значение, вес, дата обновления факта), плюс результаты проверки: справочник правил, прогон и найденную проблему.

### Стартовые данные

Загрузка при первом старте: подразделения, 20–30 целей, ключевые результаты и **два прогона** с нарушением каждого правила, чтобы было с чем сравнивать.

### Миграции

Liquibase с откатом. Выполняются **накат → откат → повторный накат** без ошибок — условие приёмки на общем стенде.

### REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/runs` | список прогонов: статус, дата снимка, с чем сравнивается, число проблем |
| GET | `/api/kkd/summary?run_id=&unit_id=` | метрики по подразделению: текущее/прошлое значение, дельта, «лучше/хуже»; разбивка по важности; счётчики new/persisting/resolved |
| GET | `/api/kkd/issues` | список проблем прогона: фильтры по подразделению, правилу, важности, статусу дельты; пагинация (limit, offset, total) |

Метрики подразделения считаются **с учётом дочерних** подразделений (каскадирование).

### Дельта

- Проблема «та же самая», что в прошлом прогоне, если совпадают **правило и объект**.
- У первого прогона сравнения нет: `previous` и `delta` равны `null`, а не `0`.
- Если прошлый прогон завершился с ошибкой — сравнение не выполняется, результаты текущего прогона показываются без дельты.

### Обработка ошибок

- Неизвестный прогон или подразделение → **404**.
- Некорректные параметры → **422**.
- Единый формат: `{"error": {"code": "...", "message": "..."}}`.

### Конфигурация

Через переменные окружения (`.env.example`), адрес БД выносится из кода. `docker compose up` поднимает сервис, PostgreSQL, миграции и стартовые данные одной командой.

## Критерии приёмки

1. Код оформлен, структура пакетов отражает архитектуру (правила / сервис / API разделены).
2. Java-сервис собирается (`mvn package`) и стартует на стенде; `docker compose up` поднимает всё одной командой.
3. Скрипты БД выполняются накат → откат → повторный накат без ошибок.
4. Метрики соответствуют бизнес-требованиям, учитывают каскадирование и дельту.
5. REST API реализует описанные эндпоинты с корректными статусами и форматом ошибок.
6. JUnit-тесты покрывают минимум 4 сценария: два правила на граничных данных, расчёт метрики, расчёт дельты.
